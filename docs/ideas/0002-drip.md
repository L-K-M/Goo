# Tool idea 0002 — Drip

> **Status: proposal.** No engine code ships with this document. If the
> idea is taken, it becomes its own implementation PR with a roadmap row
> in PLAN.md. Ideas live in `docs/ideas/`; decisions live in
> `docs/decisions/`.

**One-liner.** Hold a finger anywhere and the picture sags out of it,
downward, like wax off a candle — the app is called **Melt**orama and
nothing in it melts.

## The feel

Drip is pumped. You do not drag it; you *hold* it, and the longer you
hold the further the run travels. Content under the brush is pulled
toward the bottom of the picture, not toward your finger, so the gesture
is "put the drip here" rather than "drag the drip there" — the same
division of labour as Grow, where you choose the place and time does the
work.

The run is not a rectangle. Its length is modulated by value noise
across the horizontal axis, so a wide brush lays down several runs of
different lengths with thin necks between them: icicles, candle wax,
a Dalí clock, the bottom edge of a melting Polaroid. Hold longer and the
runs stretch and thin, because each pump stamps on top of an already
displaced field.

## Why Meltorama should have it

**1. The name promises it.** The app was renamed to Meltorama 2000 in
PR 14 and the README opens with "Goo Your Photos". There are nine
brushes and six levers, and not one of them melts anything. Every user
who opens this app because of its name is looking for this tool by the
second minute. A product whose single most memorable word describes a
capability it does not have is leaving its best joke untold.

**2. It is the only tool with a direction of its own.** Every existing
brush is either radially symmetric (Grow, Shrink, Smooth, UnGoo) or
takes its direction from the finger (Smear, Move, Smudge, Nudge). Drip
takes its direction from the *picture* — down is down regardless of how
you swiped. That is a genuinely new axis in the palette, and it is the
axis that gravity, weight, sagging, and every melting metaphor lives on.

**3. It makes the best GOOvie the app can make.** Punch a keyframe on
the untouched photo, drip for four seconds, punch again: the exported
MP4 is a face melting. That is a shareable ten-second video produced by
holding one finger down, with no strip management, no fiddling, and no
artistic skill. GOOvies are the app's most expensive feature (keyframes,
tween machinery, MediaCodec, GIF encoder) and its hardest to explain;
Drip is the demo that explains it.

**4. It is the melting *brush*, which is the version worth building
first.** A whole-frame Melt lever is the obvious sibling and is worse:
it sags everything evenly, which looks like a bad anamorphic squeeze.
The interesting melt is local — a face that runs while the wall behind
it stays put. Local first; the lever, if ever, second.

## How it works in this engine

A new `StampMode.DRIP` (shaderId 6). The kernel is directional with a
fixed direction and a noise-modulated magnitude:

```glsl
// Backward mapping: to make content appear lower, sample from higher.
float run = w * DRIP_STEP_UV * (0.35 + 0.65 * valueNoise(
        v_uv.x * 40.0, float(u_dripSeed), 3u));   // 40 = DRIP_CELLS
b = vec2(0.0, -run);
vec3 prev = texture(u_field, v_uv + b).xyz;
next = vec3(b + prev.xy, prev.z);
```

Three things fall out of the existing code for free:

- **The noise is already there and already CPU/GPU-exact.**
  `GlobalField.valueNoise` and its integer LCG hash exist because the
  Static lever needed bit-identical results on both sides (SOL-41 pinned
  the wire contract). Drip reuses them, so its runs are identical in the
  preview, in the full-resolution export, and in every replay.
- **"Down" is document down.** The field is document space; the view
  transform (PR 12's pan/zoom/rotate) lives only in `WARP_VERT`'s
  `u_view`, and export and movie passes bind identity there. So a Drip
  stroke recorded with the canvas rotated 90° still runs toward the
  bottom of the *photo* on replay. This is the correct behaviour and it
  is also the free one, which is a good sign.

  Down is **+v**, and every sign above depends on it. Stamp-space UV in
  this engine has a **top-left origin** — `Stroke.kt`'s coordinate
  block says so, and `QUAD_VERT` is deliberately not flipped so that
  "field texel v ≡ image UV v". So `fromCenter.y > 0` is *below* the
  brush center, and a *negative* `b.y` samples from higher up, which
  under backward mapping is what makes content appear lower. Only
  `WARP_VERT`, which maps to the y-up window, flips — and it is not in
  this path.
- **Elongation is the pump.** No accumulator, no per-stroke state: each
  stamp reads the field it lands on, so run length grows with hold time
  as a consequence of warp-of-warp, exactly like Grow's compounding.

The falloff is the one place Drip cannot reuse what exists. A radially
symmetric weight gives a symmetric sag — the content above the touch
point rises as much as the content below falls, which reads as a lens,
not a leak. Drip wants a lobe that **reaches downward**: normal above the
center, and below it stretched out so the weight decays over a longer
distance and the run keeps pulling well past where a round brush would
have stopped. That is a new `FalloffProfile` (`TEARDROP`), computed by
scaling the *distance metric* anisotropically before the existing
smoothstep:

```glsl
// Above center: unchanged. Below: distance compressed, so the same
// weight is reached further down — the lobe extends to ~2.2 radii
// below center and the falloff is gentler all the way.
float dy = fromCenter.y < 0.0 ? fromCenter.y : fromCenter.y * 0.45;
float distA = length(vec2(fromCenter.x, dy));
```

The direction of that factor is the tool. **Below 1 reaches down; above 1
would reach *up***, giving a brush that pulls harder above the finger
than below it — gravity backwards. Worth stating because the shape is
counterintuitive at a glance: to make a brush act *further* in some
direction you shrink the distance it measures in that direction, since
weight is a decreasing function of distance.

One honest imprecision: this is an elongated lobe, not a true teardrop.
A real drop also narrows in x as it descends, which needs the x scale
to depend on y (`fromCenter.x / (1.0 - 0.5 * clamp(dy, 0.0, 1.0))` or
similar). Worth trying during implementation; the elongated lobe is the
version whose behaviour is easy to reason about, and the noise
modulation on the run length is already doing most of the work of making
the silhouette look drip-like.

This is the first non-radial kernel in the engine, and it is worth being
explicit that it is a first: `BrushFalloff.weight(d, profile)` is
currently a function of one scalar, and TEARDROP needs the vector. The
smallest honest change is a second entry point,
`BrushFalloff.weightAniso(fromCenter, radius, profile)`, with the
existing scalar function unchanged and still the reference for
everything else.

New constants beside `RADIAL_STEP_UV`:

```kotlin
/** UV run added per pumped drip stamp at strength 1. */
const val DRIP_STEP_UV = 0.005f
/** Noise cells across the image width — the width of one run. */
const val DRIP_CELLS = 40
```

`DRIP_CELLS` is an `Int`, matching `GlobalField.STATIC_CELLS = 24` and
`SPIKE_COUNT = 8`, and it reaches the shader the way every other
constant in this engine does: **hand-mirrored as a float literal with a
sync marker**, never string-injected. `WARP_FRAG` already writes
`valueNoise(uv.x * 24.0, …)` and `sin(8.0 * phi)` against those two Int
constants. That mirroring is not incidental — core GLSL ES 3.00 has no
implicit `int` → `float` conversion (it arrives only with
`GL_EXT_shader_implicit_conversions`), so `uv.x * 24` would not compile,
and the shader literal has to carry the `.0` itself.

## Cost, risks, honest trade-offs

- **It tears at the top.** Pulling content down under the brush while
  the content above it stays put is a discontinuity by construction;
  the falloff smooths it, but a hard hold at high strength will show a
  seam where the melt begins. Mitigation is the taper, not a fix — and
  the seam is arguably correct (wax has an edge where it left).
  Smooth cleans it up, which is a nice discoverable pairing.
- **The edge of the frame.** A run near the bottom samples below the
  image and clamps, which smears the last row of pixels into a vertical
  streak. Every warp engine has this; ours already does at the frame
  edge under Bulge. Worth checking that `GL_CLAMP_TO_EDGE` is what is
  bound before shipping, and worth deciding deliberately whether a drip
  running off the bottom looks like melting (it does, a bit) or like a
  bug (it also does, a bit).
- **Another pumped tool feeds REVIEW G-6.** Drip's whole point is long
  holds — a ten-second melt is ~600 stamps in the log, and every undo,
  export and keyframe materialization replays them. Drip is the
  strongest argument yet for the field-snapshot checkpoints G-6
  describes, and it should probably not ship before them.
- **Seeded per stroke.** `u_dripSeed` above should be derived from the
  stroke, not the wall clock, and stored in the stroke, or two replays
  of the same document produce different icicles. If that seems like a
  detail, note that it is exactly the detail SOL-41 was written about.

## Declined variants

- **Gravity that follows the phone's accelerometer.** Enormously fun
  for ten seconds; a sensor permission-free but sanity-free feature
  that makes the document depend on how the user was holding the
  device, which no replay can reproduce. The engine's central promise
  is that the stroke log is the document. Declined on the same grounds
  as shake-to-reset (ANALYSIS: "Declined or gated approaches").
- **Drip in the drag direction.** That is Smear with extra steps.
- **A Melt lever instead of a brush.** See argument 4.
