# 0011 — Boing (tween easing)

- **Status:** proposed
- **Date:** 2026-08-07

**One-liner.** Give each GOOvie segment an easing curve — including one
that *overshoots the keyframe and springs back* — and the animation stops
looking like a slideshow and starts looking alive. `mix()` does not
clamp, so the overshoot is free: t = 1.15 extrapolates the warp past the
pose you punched.

## The feel

Today a GOOvie moves between two punches at a constant rate: the face
inflates smoothly and arrives. It is correct and it is inert — linear
interpolation is the visual signature of amateur animation, and it is
the first thing any animation course tells you to stop doing.

With Boing on a segment, the face inflates fast, goes *past* the pose
you punched — a little too round, a little too far — and settles back
into it with a wobble. Nothing was punched at the far end. There is no
extra keyframe. The exaggeration is generated by running the same
interpolation past its endpoint.

A small dial on the strip's segment picker: **Linear · Ease · Boing**.

## Why Meltorama should have it

**1. It is squash-and-stretch, for one scalar.** Cartoon physics is what
this app's whole aesthetic is reaching for, and it is achieved with a
curve on a number. No new field, no new stroke mode, no new memory, no
new export path. The most animation per byte available anywhere in the
codebase.

**2. The extrapolation is a gift the architecture already made.** GLSL's
`mix(x, y, a)` is defined as `x·(1−a) + y·a` and is not clamped, and
`u_tween` is a plain uniform float. Feeding it 1.15 produces the warp
field that would exist if the user had kept gooing in the same direction
past where they stopped — which is *exactly* what an overshoot means
physically. The engine has been able to do this since the tween shader
was written; nothing has ever asked it to.

**3. Two punches become an animation with timing.** The strip's cost is
per punch — goo, punch, goo, punch. Easing multiplies the expressiveness
of punches already made instead of demanding more of them. A user with
two keyframes currently has one possible movie; with three curves they
have three, and one of them is funny.

**4. It is pure, testable, and cannot break the GPU.** `MovieSpec` and
`Goovie` are already pure JVM types with unit tests, which is where the
curve lives. The riskiest thing this feature can do is produce a wrong
number, and the test suite is exactly the shape that catches that.

## How it works in this engine

**The curve.** A small enum with a pure evaluation, beside `MovieSpec`:

```kotlin
enum class Easing { LINEAR, EASE, BOING }

/** Maps segment progress [0,1] to tween t — which may leave [0,1]. */
fun Easing.at(p: Float): Float = when (this) {
    LINEAR -> p
    EASE -> p * p * (3f - 2f * p)
    // Back-out: overshoots to ~1 + OVERSHOOT, returns to exactly 1.
    BOING -> {
        val q = p - 1f
        1f + (1f + OVERSHOOT) * q * q * q + OVERSHOOT * q * q
    }
}
```

The two properties worth pinning with tests are `at(0) == 0` and
`at(1) == 1` for every curve — a segment must start and end exactly on
its keyframes, whatever it does in between — and `max(at) ≤ 1 + CAP` for
BOING.

**Where it is stored.** On the keyframe pin, describing the segment
*leaving* that pin. It is document state like the levers, serializes
into `project.json` beside the pins, and defaults to `LINEAR` for
projects saved before the schema grew — which is the whole
compatibility story, and it fits the loader's existing rule that a
document either validates or is refused rather than half-restored.

**Where it is consumed.** Two places, both of which already walk the
segment:

- the movie render walk (MP4 and GIF share it), where the per-frame
  progress becomes `easing.at(progress)` before it reaches `u_tween`;
- the live playback loop, so the preview shows the same motion the
  export will produce.

**What it does *not* touch:** the scrub. Dragging the scrub handle is
direct manipulation of position, not playback of time, and should stay
linear — the handle is the user's finger and it must go where the finger
goes. That distinction should be written into the code as a comment,
because it will otherwise be "fixed" by someone.

## Cost, risks, honest trade-offs

- **Extrapolation can fold the field.** Past a certain overshoot the
  warp beyond the keyframe self-intersects and the picture tears rather
  than exaggerates. There is no general bound available — how far is
  safe depends on the field the user painted — so the answer is a fixed,
  modest, playtested `OVERSHOOT` constant, not a lever. A slider here
  would be a tearing generator.
- **It also extrapolates the Fusion mask.** The tween mixes the whole
  `vec3`, so `z` overshoots too and is then clamped by
  `clamp(f.z, 0.0, 1.0)` in the warp pass — which means a fusion reveal
  under Boing arrives, saturates, and holds rather than wobbling. That
  is a benign asymmetry and probably the behaviour you want, but it is
  an asymmetry and someone should look at it on a real photo before
  calling it correct.
- **The globals lerp too, and they are not clamped the same way.**
  Levers are interpolated CPU-side between pins; running that lerp past
  1 can push a lever outside [−1, 1], where the analytic warps were
  never characterized. Clamp the lever lerp at the boundary while
  letting the field extrapolate: the field's overshoot is the effect,
  the levers' overshoot is undefined behaviour.
- **Interaction with ANALYSIS K3-24 (ping-pong playback).** Ping-pong
  reverses the timeline; Boing bends it. Both are transformations of the
  same progress scalar, they compose, and they should be designed
  together or the second one to land will re-open the first.

## Declined variants

- **A general easing editor (bezier handles).** Wrong app. Three
  detents, chosen well, beat a curve editor nobody will open on a phone.
- **Per-keyframe ease-in/ease-out pairs.** Doubles the state for a
  refinement that only a user who already knows animation would notice —
  and that user has After Effects.
- **Spring physics with mass and damping instead of a curve.** More
  "real", more parameters, and non-analytic: a simulated spring is
  stateful and would have to be sampled identically in preview and
  export or the movie would not match. A closed-form curve is
  reproducible by construction, which is the same reason
  `GlobalField`'s noise is an integer hash rather than a sin-hash.
